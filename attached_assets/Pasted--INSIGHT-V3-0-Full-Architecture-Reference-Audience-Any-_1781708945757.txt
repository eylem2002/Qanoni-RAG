## 1. Project Overview

INSIGHT V3.0 is a full-stack internal ERP/management platform. It manages **leads, calls, performance, compensation, employees, inventory, quality control, and HR** for a high-traffic contact-center environment.

The system is a **Node.js monolith backend** paired with a **React SPA frontend**, backed by MySQL, Redis, Snowflake, and GCP infrastructure.

## 4. Backend — Deep Dive

### 4.1 Entry Points

#### `backend/server.js` — Cluster Manager
- Forks multiple worker processes using Node.js `cluster` module
- Handles graceful shutdown and worker respawn
- Runs only in production; dev runs a single process directly via `app.js`
- **Does not contain any business logic** — only process management

#### `backend/app.js` — Worker Entry Point
- Called by each cluster worker (and directly in dev)
- Runs the bootstrap sequence: env → logger → db → redis → sessions → queues → routes → API
- Starts the Express HTTP server after all infra is confirmed healthy

---

### 4.2 Bootstrap Layer

`backend/src/bootstrap/` — Each file is a single-responsibility initializer. They are called in order inside `app.js`. **Never put business logic here.**

| File | Responsibility |
|---|---|
| `initEnv.js` | Load and validate all environment variables via `env.schema.js`. App crashes here if any required var is missing. |
| `initLogger.js` | Set up the global logger (Winston or equivalent). Must run before anything else that logs. |
| `initDb.js` | Open MySQL connection pools (write, read, reports) and verify health. Also initializes Snowflake if configured. |
| `initRedis.js` | Connect to Redis, verify health. App can continue if Redis is down but with degraded caching. |
| `initSessions.js` | Mount Express session middleware with Redis store. |
| `initTokens.js` | Initialize session token management for cross-worker sync. |
| `initQueues.js` | Set up BullMQ queues and Google Pub/Sub subscriptions. |
| `initJobs.js` | Register recurring jobs (e.g., log flushing). Only runs on primary worker. |
| `initEmail.js` | Configure nodemailer or equivalent email transport. |
| `initProxy.js` | Mount Cloud Run proxy middleware if enabled. |
| `initApi.js` | Create the Express app, apply CORS, body parsers, and return the `app` instance. |
| `initRoutes.js` | Import all domain routes and register them on the Express app. |
| `initLogsFlush.js` | Schedule periodic log flushing to persistent storage. |

### 4.3 API Layer (Middleware + Routes)

#### `backend/src/api/middlewares/`

Middleware runs on **every request** (global) or on **specific routes** (route-level). The pipeline order matters.

| File | Type | Responsibility |
|---|---|---|
| `context.js` | Global | Attaches a per-request execution context object to `req`. Used downstream for tracing. |
| `processRequest.js` | Global | Decodes session, attaches `req.user`, `req.permissions`. The main auth gate — all authenticated routes depend on this running first. |
| `rateLimiter.js` | Global | Two limiters: `apiRateLimiter` (all routes) and `loginRateLimiter` (stricter, auth routes only). Backed by Redis. |
| `requestLogger.js` | Global | Logs every incoming request with method, path, user, and response time. |
| `errorHandler.js` | Global (last) | Catches all errors thrown downstream, maps them to proper HTTP status codes, and returns structured JSON error responses. Must be the last middleware registered. |
| `notFoundHandler.js` | Global (last-1) | Catches any request that reached no route and returns `404`. Registered just before `errorHandler`. |
| `checkAccess.js` | Route-level | Reads `req.user.permissions` and checks if the user *has* a given permission. Does not throw — returns a boolean. Used by UI-gating logic. |
| `requireAccess.js` | Route-level | Same as `checkAccess` but **throws** `SecurityError` if the user lacks the permission. This is what protects every actual API endpoint. Usage: `requireAccess({ resource: 'inventory', action: 'view' })`. |
| `validator.js` | Route-level | Wraps Joi schema validation. Call `validate(schema)` as middleware on a route to reject bad input before the controller runs. |
| `uploadSafety.js` | Route-level | Validates file uploads: allowed MIME types, max size, malicious filename detection. |
| `refreshPermissions.js` | Route-level | Triggers a permission cache refresh for the current user. Used after IAM changes. |
| `syncSessionTokens.js` | Route-level | Syncs session tokens across cluster workers via Redis pub/sub. |
| `index.js` | — | Barrel export for all middleware. |

#### `backend/src/api/routes/`

| File | Responsibility |
|---|---|
| `index.js` | **Main route registry.** Imports every domain's router and mounts it on the Express app with its base path (e.g., `/api/inventory`). This is the single source of truth for all API paths. |
| `health.routes.js` | `/health` endpoint — returns system health (DB, Redis, process). Used by GCP load balancer. |
| `internal.routes.js` | Internal/admin endpoints not exposed to the public. |

### 4.5a DB Query Fundamentals (`infra/db/`)

This is the lowest-level layer every domain repo touches. Understanding it is mandatory before writing any SQL.

---

#### `pools.js` — Connection Pool Initialization

Called once during bootstrap (`initDb.js`). Creates and holds three MySQL pools as module-level singletons.

```
WritePool   → MySQL primary   (always created)
ReadPool    → MySQL replica   (falls back to WritePool if not configured for this ENV profile)
ReportsPool → MySQL replica   (falls back to WritePool if not configured for this ENV profile)
```

**How fallback works:** `ENV_PROFILES[NODE_ENV]` has boolean flags `readDb` and `reportsDb`. In `development`, both are usually `false`, so all three variables point to the same `WritePool`. In `production`, each points to its own dedicated host.

```js
// pools.js
ReadPool = profile.readDb
  ? mysql.createPool({ ...config.db.read, ... })
  : WritePool;                                   // ← fallback
```

A separate **PostgreSQL** pool (`PostgresPool`) is also initialized here for the IAM system and exposed via `getPostgresPool()`.

**Rules:**
- `initPools()` must be called before any query runs — enforced by `getPools()` throwing if `WritePool` is null
- Never import `WritePool` / `ReadPool` directly — always go through `getPools()`

---

#### `query.js` — The Single Query Gateway

**Every DB call in the entire backend goes through this one function.** Repos never touch a pool directly.

```js
export async function query(sql, params = [], options = {})
```

**Signature:**

| Argument | Type | Required | Description |
|---|---|---|---|
| `sql` | `string` | ✅ | SQL with `?` placeholders |
| `params` | `Array` | ✅ (default `[]`) | Bound values — never string-interpolate |
| `options.role` | `'write' \| 'read' \| 'reports'` | ✅ | Which pool to use |
| `options.tag` | `string` | — | Label that appears in error logs |
| `options.timeout` | `number` | — | Per-query timeout in ms |
| `options.connection` | `PoolConnection` | — | Pass a transaction connection here |

**What it does internally (in order):**

1. **Guards** — throws `DBError` immediately if:
   - `role` is missing
   - `role` is not one of `write | read | reports`
   - A write statement (`INSERT`, `UPDATE`, `DELETE`, `REPLACE`, `CREATE`, `DROP`, `ALTER`, `TRUNCATE`, `RENAME`, `GRANT`, `REVOKE`) is attempted with `role !== 'write'`

2. **Pool resolution** — calls `resolvePool(role)` to get the correct `mysql2` pool

3. **Executor selection** — uses `options.connection` if provided (for transactions), otherwise uses the pool directly

4. **Protocol selection** — mysql2 has two execution modes:
   - `execute()` → prepared statements (binary protocol, faster, safer for simple params)
   - `query()` → text protocol (required when any param is itself an array, e.g. `IN (?)` with `[1,2,3]`)
   - `shouldUseQueryForArrayExpansion(params)` checks for nested arrays and picks the right mode automatically

5. **Error handling** — on failure: logs `role`, `tag`, `durationMs`, `err.message`, `mysqlCode`, `mysqlErrno`, then re-throws as `DBError`

**Usage in a Repo:**

```js
// READ — operational query
import { query } from '../../../infra/db/query.js';

export function getAgentById(agentId) {
  return query(
    'SELECT id, name, status FROM agents WHERE id = ?',
    [agentId],
    { role: 'read', tag: 'agents.getById' }
  );
}

// WRITE
export function updateAgentStatus(agentId, status) {
  return query(
    'UPDATE agents SET status = ?, updated_at = NOW() WHERE id = ?',
    [status, agentId],
    { role: 'write', tag: 'agents.updateStatus' }
  );
}

// READ with IN () — array param, uses text protocol automatically
export function getAgentsByIds(ids) {
  return query(
    'SELECT id, name FROM agents WHERE id IN (?)',
    [ids],                    // ← ids is an array → query() used instead of execute()
    { role: 'read', tag: 'agents.getByIds' }
  );
}

// REPORTS — heavy aggregation
export function getMonthlyLeadStats(month) {
  return query(
    'SELECT department_id, COUNT(*) AS total FROM leads WHERE MONTH(created_at) = ? GROUP BY department_id',
    [month],
    { role: 'reports', tag: 'leads.monthlyStats' }
  );
}
```

**Critical rules for Repo authors:**
- Always pass `role` — the query will throw without it
- Never pass write SQL with `role: 'read'` or `role: 'reports'` — it will throw immediately
- Always use `?` placeholders — never string-concatenate user input into SQL
- Use `tag` on every query — it makes debugging log output usable
- Pass `options.connection` when inside a `withTransaction()` callback

---

#### `transactions.js` — Atomic Multi-Query Operations

Use `withTransaction` when two or more writes must succeed or fail together.

```js
export async function withTransaction(fn)
```

**What it does:**
1. Gets a connection from `WritePool`
2. Calls `BEGIN`
3. Runs your callback `fn(connection)`
4. On success → `COMMIT`, releases connection, returns `fn`'s return value
5. On any error → `ROLLBACK` (failure to rollback is swallowed so the original error is not masked), releases connection, re-throws as `DBError`

**Usage:**

```js
import { withTransaction } from '../../../infra/db/transactions.js';
import { query } from '../../../infra/db/query.js';

export async function transferItem(itemId, fromAgent, toAgent) {
  return withTransaction(async (conn) => {
    await query(
      'UPDATE inventory SET assigned_to = ? WHERE id = ?',
      [toAgent, itemId],
      { role: 'write', connection: conn }   // ← pass the transaction connection
    );
    await query(
      'INSERT INTO inventory_log (item_id, from_agent, to_agent, ts) VALUES (?, ?, ?, NOW())',
      [itemId, fromAgent, toAgent],
      { role: 'write', connection: conn }
    );
  });
}
```

**Rules:**
- `withTransaction` always uses `WritePool` — never use it for reads
- Every `query()` call inside the callback **must** receive `connection: conn` — otherwise it opens a separate connection outside the transaction
- Do not catch errors inside the callback — let them propagate so `withTransaction` handles the rollback

---

#### `postgres.js` — IAM Database

The IAM system (`domains/iam/`) uses a separate PostgreSQL database. The `pg.Pool` is initialized via `initPostgresPool()` and retrieved via `getPostgresPool()`.

```js
import { getPostgresPool } from '../../../infra/db/postgres.js';

const pg = getPostgresPool();
const { rows } = await pg.query('SELECT * FROM policies WHERE entity_id = $1', [entityId]);
```

Note: Postgres uses `$1, $2, ...` placeholders, not `?`. The `query.js` gateway does **not** wrap Postgres — IAM repos call `pg.query()` directly.

## 6. Domain Pattern (The Golden Rule)

Every backend domain — without exception — must follow this 4-layer pattern:

```
controller.js  →  logic/[Name]Logic.js  →  repos/[Name]Repo.js  →  DB
```

### What Goes Where

#### `routes.js`
- Import `express.Router()`
- Define HTTP method + path
- Apply middleware (`requireAccess`, `validate`)
- Call the controller method
- **No logic, no DB calls, no business decisions**

```js
import { requireAccess } from '../../../api/middlewares/index.js';
import { validate } from '../../../core/validation/joiValidator.js';
import * as controller from './controller.js';
import { addItemSchema } from './validation.js';

router.get('/get-inventory',
  requireAccess({ resource: 'inventory', action: 'view' }),
  controller.getInventory
);

router.post('/add-item',
  requireAccess({ resource: 'inventory', action: 'create' }),
  validate(addItemSchema),
  controller.addItem
);
```

#### `controller.js`
- Extract data from `req` (params, body, user, query)
- Call one `Logic` method
- Send the response
- **No SQL, no Redis, no business rules — just wire `req` → logic → `res`**

```js
import * as InventoryLogic from './logic/InventoryLogic.js';

export async function getInventory(req, res, next) {
  try {
    const { departmentId } = req.query;
    const data = await InventoryLogic.getInventory(departmentId, req.user);
    res.json({ success: true, data });
  } catch (err) {
    next(err);
  }
}
```

#### `logic/[Name]Logic.js`
- All business rules live here
- Can call Repo methods, Redis, other services
- Throws typed errors (`ValidationError`, `NotFoundError`) when rules are violated
- **No `req`/`res` objects — pure functions that take plain args and return plain data**

```js
import * as InventoryRepo from '../repos/InventoryRepo.js';
import { cache } from '../../../infra/redis/cache.js';
import { NotFoundError } from '../../../core/errors/index.js';

export async function getInventory(departmentId, user) {
  const cacheKey = `inventory:dept:${departmentId}`;
  const cached = await cache.get(cacheKey);
  if (cached) return cached;

  const items = await InventoryRepo.findByDepartment(departmentId);
  if (!items.length) throw new NotFoundError('no inventory for this department');

  await cache.set(cacheKey, items, 300);
  return items;
}
```

#### `repos/[Name]Repo.js`
- All SQL lives here
- Uses `infra/db/query.js` — never raw pool directly
- Returns plain objects/arrays
- **No business logic, no cache, no errors other than re-throwing DBErrors**

```js
import { query } from '../../../infra/db/query.js';

export async function findByDepartment(departmentId) {
  return query(
    'SELECT * FROM inventory_items WHERE department_id = ? AND is_active = 1',
    [departmentId]
  );
}

export async function insertItem(data) {
  return query(
    'INSERT INTO inventory_items (name, department_id, assigned_to) VALUES (?, ?, ?)',
    [data.name, data.departmentId, data.assignedTo]
  );
}
```

## 7. Request Lifecycle

A full round-trip from browser to database and back:

```
Browser
  │
  ▼
Nginx (SSL termination, reverse proxy)
  │
  ▼
Express App
  │
  ├─ rateLimiter          ← Check Redis for rate limit
  ├─ context              ← Attach trace context to req
  ├─ processRequest       ← Decode session, attach req.user
  ├─ requestLogger        ← Log the incoming request
  │
  ├─ [route matched]
  │   ├─ requireAccess    ← Check IAM permissions (throws 403 if denied)
  │   ├─ validate         ← Joi schema validation (throws 400 if invalid)
  │   └─ controller       ← Extract args, call Logic
  │       └─ Logic        ← Business rules, cache check
  │           └─ Repo     ← SQL query via infra/db/query.js
  │               └─ MySQL (write / read / reports pool)
  │
  ├─ notFoundHandler      ← If no route matched
  └─ errorHandler         ← Maps errors to HTTP responses

Browser ← JSON response
```

## 8. Database Strategy

### Pool Routing

| Query Type | Pool Used | When |
|---|---|---|
| `INSERT`, `UPDATE`, `DELETE` | Write Pool | Always for mutations |
| `SELECT` (operational) | Read Pool | Regular reads (replicated from write) |
| `SELECT` (reports/analytics) | Reports Pool | Heavy aggregations, cross-domain reports |

The `infra/db/query.js` function detects the query type and routes automatically. You can also explicitly specify the pool.

### IAM (PostgreSQL)

The IAM system uses a **separate PostgreSQL database** (`infra/db/postgres.js`). This isolates permission data from the operational MySQL database.

### Snowflake (Reporting)

Heavy analytical queries that would strain MySQL go to Snowflake. The `reports/` domain uses this pool. Historical data, cross-period aggregations, and BI-style queries live here.

### Transaction Pattern

```js
import { transaction } from '../../../infra/db/transactions.js';

await transaction(async (conn) => {
  await conn.query('UPDATE leads SET status = ? WHERE id = ?', ['closed', leadId]);
  await conn.query('INSERT INTO lead_events (lead_id, event) VALUES (?, ?)', [leadId, 'closed']);
});
```

## 9. IAM & Authorization

### How It Works

1. On login, the user's permissions are fetched from PostgreSQL and stored in their Redis session
2. `processRequest.js` middleware attaches permissions to `req.user.permissions` on every request
3. `requireAccess({ resource, action })` checks `req.user.permissions` and throws `SecurityError` if the user lacks the grant
4. The frontend `usePermission(resource, action)` hook reads the same permission set (synced from the session) to show/hide UI elements

### Permission Model

```
resource: 'inventory'
action:   'view' | 'create' | 'edit' | 'delete' | 'export'
```

### IAM Admin Portal

The `portals/iam/` frontend and `domains/iam/` backend together form the IAM management UI, where admins manage resources, actions, policies, templates, and grants.

## 10. Error Handling

### Backend

Throw typed errors from Logic. They bubble up through the Controller to `errorHandler.js`, which maps them to HTTP responses:

```js
// In Logic:
throw new ValidationError('start date must be before end date');

// errorHandler.js automatically sends:
// HTTP 400: { success: false, error: 'start date must be before end date' }
```

### Frontend

The Axios interceptor in `apiClient.js` catches HTTP errors. Components use React Query's `onError` callback or try/catch in mutations. The `uiSlice.js` holds global snackbar state for showing error toasts.

| `domain/logic/*.js` | Business rules, validation logic, cache interaction | Raw SQL, `req`/`res` objects, HTTP concerns |
| `domain/repos/*.js` | SQL queries, DB calls via `query.js` | Business rules, caching, HTTP concerns |
| `infra/**/*.js` | Infrastructure clients and abstractions | Business logic, domain knowledge |
| `core/errors/*.js` | Error class definition | Logic, DB calls |
| `core/utils/*.js` | Pure utility functions | Side effects, DB/Redis calls |

| Portal `portal/[Name]Portal.jsx` | Layout, tab structure, top-level context | Direct API calls (use hooks), styling details |
| Portal `apis/[name]Apis.js` | All `apiClient` calls for this portal | Component code, business logic |
| Portal `hooks/use*.js` | React Query queries/mutations, local state | API call implementations |
| Portal `helpers/[name]Helpers.js` | Pure JS utility functions for this portal | React hooks, API calls |
| `components/ui/` | Generic presentational components | Business logic, API calls |
| `app/store/slices/` | Redux slice (state shape, reducers, actions) | API calls, side effects (use RTK Query or React Query instead) |
